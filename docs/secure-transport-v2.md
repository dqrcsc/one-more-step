# 安全传输 v2

本文件说明 v1.4.0 候选实现的协议与升级方式；编译、测试和真机部署结果分别记录，不能用协议说明代替验收。冻结的字段与测试向量见 [实施计划](superpowers/plans/2026-10-27-secure-transport.md) 和 `shared-protocol/test-vectors/secure-v2.json`。

## 用户可见的变化

- Mac 与 Android 必须同时升级。旧配对没有 v2 安全标记，需要重新配对一次；不卸载 App、不清空收件数据。
- 手机输入 Mac 本地 `oms pair` 显示的完整 `oms://pair?v=2...` 链接。链接含 256 位一次性秘密，10 分钟有效；按密码对待，不公开或经旧明文 OMS、HTTP 页面传送。
- 取消输入 6 位码通过 HTTP 换取完整链接的入口；远程 `/pair/resolve` 不再返回配对凭据。当前 App 保留粘贴完整链接，不承诺具备内置扫码器。
- 握手失败、旧版本、错误标签、乱序或重放均拒绝，不回退明文。重新配对仍撤销旧连接和待返回操作。
- OTA 继续使用 Android 覆盖安装；升级期间新手机无法使用旧主机是预期行为。完成 Mac 切换和新配对后恢复。

## 连接如何建立

1. Mac 发出协议 v2、设备标识、随机数和本次连接的临时 P-256 公钥。
2. 手机用一次性配对秘密（首次）或 v2 配对密钥（重连）认证完整握手上下文，并发送自己的临时公钥与随机数。
3. Mac 验证手机证明、返回自己的证明。双方分别做 P-256 ECDH 与 HKDF 派生；长期密钥不出现在网络响应中。
4. 手机发送加密的 finish，Mac 验证并回送加密确认，随后才允许业务操作。设备遥测、手机名称等在加密 finish 内传输。
5. 每条物理连接使用独立加密上下文。RPC、文件头/内容/ACK、心跳均使用 AES-256-GCM；密钥按方向分离，递增序号构造 nonce，并认证记录头、方向与会话身份。

每方向达到 1 GiB 明文或 2^20 条记录时拒绝继续使用该密钥并重连，不能重置同一密钥的计数器。文件发送仍以匹配的对端落盘 ACK 作为交付依据；加密不改变收件索引、文件限额或 GUI 人工确认语义。

## 明确边界

- 这是一套使用平台密码库的应用层组合协议，不是 TLS 或 Noise 实现，也未经过第三方密码协议审计。
- 握手设备标识、端点地址、消息长度和时序仍可被观察；HTTP 发现/安装页面不作为可信身份依据。业务内容在认证加密记录内。
- 安全依赖一次性完整链接通过用户控制的可信途径进入手机。泄露该链接允许在其有效期内争抢配对；短有效期和单次消费不能替代秘密保管。
- 不保护被控制的 Mac/手机、屏幕泄露、剪贴板泄露或本地备份。运行时采用临时 ECDH 密钥，不把“尽力清理内存”描述成可证明的完整擦除。
- BLE 使用同一保护边界，但现有 MTU/背压能力仍未专项修复。Mac 蓝牙桥没有关闭指定 central 的 API；协议失败后销毁会话并拒绝后续帧，需真实断开重连，不声称已物理断链。
- WAN 仍是 WebSocket 中继接入，尚无生产 relay 的真机验收；不能把 LAN 测试外推为 BLE/WAN 可用性证明。
- APK 下载暂仍使用 HTTP；已安装 App 的覆盖升级由 Android 检查签名一致性。HTTP hash 元数据不是独立可信来源，也不能证明首次安装的分发安全。
- 双端配对保存不是分布式事务。网络断开或进程崩溃可导致两端状态不一致；需明确重配，不自动使用旧密钥或明文路径掩盖失败。
