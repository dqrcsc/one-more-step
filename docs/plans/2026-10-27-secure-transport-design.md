# 安全配对与加密传输设计提案

日期：2026-10-27。基线：`da30d71` / v1.3.9。状态：用户于 2026-10-27 确认推荐方案及一次重新配对、取消 HTTP 短码入口、拒绝明文回退的取舍。实施开始时尚未修改运行服务或手机版本。

## 当前问题与成功标准

源码确认：`handlePairRequest` 在明文配对响应中返回 `pairSecretHex`；`/pair/resolve?pin=...` 经 HTTP 返回含一次性 token 的完整链接；认证后的 RPC、文件、ACK 与心跳仍为明文。Android `auth.response` 还在认证完成前携带设备遥测。已有 HMAC 挑战应答是身份认证，不提供内容保密。

成功标准：首次配对凭据不经网络明文取回；长期配对密钥不出现在网络响应；业务帧完整认证加密；错误密钥、篡改、重放、跨连接帧和降级均失败关闭；两端使用相同测试向量；OTA 后完成新配对、双向投递、重连与 GUI 确认真机验证。保留现有收件数据和文件 ACK 语义。

## 方案比较与建议

| 方案 | 优点 | 代价 / 缺口 |
|---|---|---|
| 仅局域网 TLS + 固定证书 | 复用成熟 TLS，直接保护 LAN | BLE 与转发中继仍需另外处理；必须禁用这些明文回退才能保证连接切换不泄露 |
| 统一应用层会话加密（建议） | 一个加密入口覆盖现有三种传输，不修改业务 RPC | 必须严格定义握手、序号、方向和失败状态；组合协议不是已审计的 TLS/Noise 实现 |
| 引入成熟 Noise 协议实现 | 复用规定好的握手模式 | 需要选择、验证 Bun 与 Android 两端实现及互操作；增加依赖与维护范围，尚未完成库适配调查 |

本批建议第二种；不以“使用标准算法”代替协议审查。实现前冻结线格式与双端向量，测试不通过不切换用户的运行服务。

## 配对与身份

- 新配对 URI 标记 v2，使用密码学随机的 256 位一次性 token，有效期 10 分钟。仅通过 Mac 本地 CLI / 本地页面展示。保留 Android 现有完整 URI 输入；不假设当前 App 有扫码器，不把新增扫码器作为本批前提。
- 删除远程 PIN 换取完整链接入口及对应安装页操作。旧 6 位码和旧 URI 给出明确升级提示；不继续保留可获取密钥的兼容后门。HTTP 安装页可继续提供 APK 下载。
- 用户需通过自己控制的可信途径把完整 URI 输入手机；不得通过旧 OMS 明文推送、远程 HTTP 页面或公开聊天传递新 token。若日后需要只输入短码配对，应另用经过验证的 PAKE 方案，不能把 6 位码直接当加密密钥。
- 首次握手用一次性 token 认证整个握手上下文；长期配对密钥由握手密钥材料派生，两端各自保存，不由 Mac 明文下发。Mac ID、手机 ID、协议版本、握手用途、双方随机数与临时公钥都纳入认证。
- 现有 Android 的 `pub_<phoneId>` 只是标识字符串，不当作真实公钥。新会话使用真实临时 EC 公钥，现有身份标签仅作绑定标识。
- 配对凭据成功后一次性消费；同时请求只允许一个完成。认证成功并收到对端密钥确认后才替换可信设备、撤销旧会话。失败或超时不清空用户原配对和收件记录。响应丢失需有明确的同连接幂等处理；进程崩溃导致双端配对状态不一致时明确要求重新配对，不伪报成功。

## 会话与帧

- 每条物理连接建立独立会话，采用临时 P-256 ECDH、HKDF-SHA256、AES-256-GCM；密码学运算使用 Bun/Node 与 Android/JCA 的现成实现，不自行实现椭圆曲线或 AES。
- 已配对重连以新的配对密钥认证；初次配对以一次性 token 认证。两种用途使用不同域标签，拒绝将一次配对证明当作重连证明。
- 双向密钥分离，双端密钥确认分离；握手 transcript 用固定字段顺序和长度编码，禁止简单冒号拼接任意输入。限定字段长度、合法编码、曲线和公钥格式。新连接更换临时密钥和随机数。
- 状态顺序为未认证 → 握手中 → 密钥确认 → 可用。未确认前不广播上线、不刷新业务队列、不接受状态遥测。明文握手只容纳限定消息，不包含手机状态、通知正文、文件名等业务内容。
- 保留既有业务帧，在外层增加加密记录。完整业务帧作为密文；记录版本、方向、会话绑定、序号和长度纳入认证。接收先校验上限，再解密验签，成功后才解析业务内容。
- 每方向独立递增序号并确定性构造 96 位 GCM nonce；同一密钥绝不复用 nonce。加密在最终发出时、优先级出队后完成；Android 对取号、加密和发出串行化，避免并发乱序。序号耗尽或达到规定密钥使用限额前断开并重新握手。
- 现有传输按有序字节流处理，接收要求下一序号严格匹配。拒绝重复、跳序、跨会话、错误标签、未知套件和连接建立后的明文业务帧；失败立即撤销该连接的加密上下文和等待请求，不自动明文回退。
- RPC、文件头、文件块、ACK、心跳、异步手机通知均走唯一的受保护发送入口。初次配对临时 WebSocket 接收器也必须切换到同一受保护处理路径，不能留下单独的明文旁路。
- BLE / WAN 接入相同保护边界。BLE 现有 MTU/背压和 WAN 部署问题不在本批修复；没有真机证据时不能声称这些链路可用。无法承载安全握手时应失败，不回退明文。

## 升级与部署

- 候选版本暂定 v1.4.0 / Android code 14，反映配对协议不兼容；发版前重新检查版本占用。
- 先完成双端代码、互操作与负面测试，签名匹配和本地备份，再用旧主机提供新 APK 的 OTA 下载。Android 系统完成安装后，新手机暂时无法与旧主机建立业务会话，这是预期的拒绝降级。
- 再切换 Mac 主机到新版本，并由用户输入新的完整配对链接完成一次配对。不卸载 App、不清空收件箱。旧配置保留在受限本地备份，新版本明确标记旧记录“需重新配对”，不能当作安全 v2 记录。
- 旧密钥曾明文传输，不能静默升级其可信级别。回退也不得自动放开明文；Android 低 versionCode APK 无法保证直接覆盖降级，回退需另行构建高版本码的同签名包。
- APK 暂继续经 HTTP 下载，Android 已安装应用的签名验证负责覆盖安装身份；HTTP 元数据/hash 本身不作为独立信任凭据。不宣称此次覆盖 OTA 全链路保密或首次安装的信任分发。
- 本批不推送 GitHub、不发布 Release，除非用户另行要求。

## 验证矩阵与验收证据

1. 纯模块：RFC HKDF 向量、GCM 已知向量，固定握手输入在 Bun/JVM 得到相同密钥和密文，双向交叉解密；错误密钥/标签、篡改头/密文、重放/乱序、反射、跨会话、截断和长度边界全部拒绝。
2. 握手：错误 token、错设备、过期/重复配对、并发配对、旧 URI、旧配对、伪造 ACK、握手超时、重连随机数更新；任何失败不得触发业务回调或覆盖已存可信记录。
3. 接入：WebSocket 模拟双端全握手 → RPC → 文件/ACK → 重连；抓取合成测试原始字节，确认无 token、pairSecret、遥测、文件名或测试正文。扫描所有发送调用以检查旁路，测试旧明文帧明确失败。
4. 工程：TypeScript、Bun 测试、Android JVM/Kotlin/APK；不得只以编译或两端各自 round-trip 证明互操作。
5. 真机 LAN：OTA 安装和新配对、0 字节与多块文件投递、手机到 Mac 合成标记、断开重连、手机 GUI 拒绝/放行与换页拒绝。只保存过滤后的诊断证据，不记录真实密钥或屏幕正文。
6. 加密不会隐藏连接端点、长度、时间和握手标识；不保护已被控制的端点、磁盘备份或屏幕泄露。未审计的组合协议与未完成 BLE/WAN 真机验收必须保留为限制说明。

## 原始规范与平台依据

- [RFC 5869：HKDF](https://www.rfc-editor.org/rfc/rfc5869)：密钥派生与用途隔离依据。
- [NIST SP 800-38D](https://csrc.nist.gov/pubs/sp/800/38/d/final)：GCM 认证加密及 nonce 唯一性要求。
- [Android KeyAgreement](https://developer.android.com/reference/javax/crypto/KeyAgreement)：ECDH 从 API 11 提供；本项目 minSdk 为 30。实际互操作仍需本机 Bun/JVM 与目标 Android 验证。
